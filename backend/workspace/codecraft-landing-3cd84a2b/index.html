FIG. 02 — DESIGN PRINCIPLES

We treat code like a load-bearing structure.

§1

Draft first, execute second

Every function starts as a pencil sketch: inputs named, edge cases annotated, failure modes drawn in the margin before a single test runs.

§2

Tolerances, not vibes

Good code states its tolerances — what it accepts, what it rejects, where it breaks. We teach you to letter those boundaries explicitly.

§3

Reviewed like a drawing set

Your pull requests get red-pencil markup from working engineers, the same way a blueprint gets redlined before it goes to the shop floor.

§4

Built to be re-read

We optimize for the engineer who inherits your code in three years, not for the version that merely compiles today.

FIG. 03 — TWELVE-WEEK SEQUENCE

Four phases, one drawing set.

  1. 01

    Blueprint

    Weeks 1–3

    Problem decomposition, data modeling, and system sketches on whiteboard and paper before any code is written. You learn to draft an interface the way you'd draft a floor plan.

  2. 02

    Joinery

    Weeks 4–6

    Where pieces meet. APIs, modules, and services are fitted together with the same care a joiner gives a dovetail — tight, load-tested, no visible gaps.

  3. 03

    Finish

    Weeks 7–9

    Sanding down the rough edges: readability, naming, error handling, and the quiet details that separate working code from well-made code.

  4. 04

    Ship

    Weeks 10–12

    A capstone system, built solo and reviewed like client work — deployed, documented, and defended in a live crit with practicing engineers.
